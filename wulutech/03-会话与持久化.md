# 03 — 会话与持久化：从线性历史到图

> 源码锚点：`packages/durable/src/types.ts:51-362` / `packages/durable/src/memory-storage.ts:112` / `packages/coding-agent/src/core/session-manager.ts:1746` / `packages/agent/src/harness/session/`

---

## 1. 问题：线性历史为什么不够用

一个真实的长程会话可能是这样的：

```
第 1 轮：用户说“加一个图像压缩的端到端用例”→ Agent 读代码、写实现、跑测试
第 2 轮：用户说“改成分辨率自适应”→ 在第 1 轮成果上继续改
第 3 轮：用户说“刚才的方案保留，再试一种用 WASM 的”→ 需要分叉出两条路径
第 4 轮：上下文用了 80%，需要压缩但保留最近 20 条 → 需要在不丢分支信息的前提下摘要
```

如果历史只是线性的 `messages[]`（`[user, assistant(toolCall), toolResult, ...]`），会遇到三类困难：

- **分叉难**：没有 `parentId`，分叉只能深拷贝整个数组，分支间无法共享前缀，浪费存储与 token。
- **压缩即丢失**：直接截断旧消息会丢掉分支信息；摘要与原始记录的关系无法描述。
- **并发与恢复无法建模**：中途插队的 `steer` 消息与主分支如何共存？崩溃后从哪条记录恢复？

Pi 的答案分两代。**现役**（`coding-agent` 实际在跑的）已用 `SessionManager` 的追加日志实现了图结构；**下一代**（`0.86.0` 新增的 `pi-durable`）则把这张图形式化为四张表，作为未来 Harness 的统一契约。本章先讲通用的图直觉，再对照两代实现。

---

## 2. 直觉：会话是一份只追加的图

想象一份只追加的日志，每行是一条 `Entry`：

```
id=1  kind="message"  head=1   ← 会话起点，head 标记“从这里开始可见”
id=2  kind="message"  parent=1
id=3  kind="message"  parent=2
id=4  kind="compaction" head=4 ← 压缩点：id≤3 的历史被摘要替代，可见范围从 4 开始
id=5  kind="message"  parent=4
```

`head` 的含义是“可见范围的起点”。读取时从 `head` 往后才是当前上下文，之前的记录虽仍存储但不再发给模型。`findLatestHeadMarker` 就是找到最近的这个起点（`packages/durable/src/memory-storage.ts:236`）。

**分叉**则通过创建新的 `Conversation` 实现：

```ts
// packages/durable/src/types.ts:20-33
type ConversationRecord = {
  id: Id; // 图中的一个分支
  parent?: { conversationId: Id; at: Id }; // 从哪个分支的哪条记录分叉
  owner?: { conversationId: Id; taskId: Id }; // 仅任务拥有的分支有此字段
};
```

```
分支 A: [1]→[2]→[3]→[4(head)]→[5]
                      │
分支 B:  parent={ conversationId:A, at:3 } → [6]→[7]
         可见范围 = A 的 [1..3] + B 的 [6..]
         读取 B 时会自动沿 parent 链回溯到 A，继承前缀
```

这样“试两条修复路径”只需新建一个分支，共享前缀零拷贝；`branchSummary` 与 `compaction` 各写一条记录来描述摘要与新旧范围的对应关系。

> 术语说明：现役的 `SessionManager` 用 `parentId`（字符串 `uuidv7`）指向上一条记录；新契约的 `durable` 用 `ConversationRecord.parent.at`（数字 `Id`）描述分叉点。二者语义一致，只是新契约把“分支”提升为一等概念（`Conversation`），而旧实现把分支隐含在 `parentId` 链中。

## 3. 现役实现：`SessionManager` 的 JSONL 图

`SessionManager`（`packages/coding-agent/src/core/session-manager.ts:1746`）是目前实际持久化的路径：

```ts
SessionHeader { version, id: uuidv7, model?, thinkingLevel?, createdAt } // 文件首行
SessionEntry = SessionMessageEntry | CustomMessageEntry | CompactionEntry 
             | BranchSummaryEntry | FileEntry | ModelChangeEntry | ...
// 每条含 id: uuidv7, parentId, timestamp，每行一个 JSON（JSONL 格式）
```

文件位置：`~/.pi/agent/sessions/<uuid>.jsonl`（或项目内的 `.pi/sessions/`）：

```
第 1 行: SessionHeader
第 2 行: SessionEntry { id:"01J...", parentId:"01H...", type:"message", message:{role:"user"...} }
第 3 行: SessionEntry { id:"01K...", parentId:"01J...", type:"message", message:{role:"assistant"...} }
...
```

- `migrateSessionEntries()` 负责跨版本迁移；`getLatestCompactionEntry()` 定位最近压缩点；`buildSessionContext()` 将记录列表还原为 `TranscriptContext`。
- 与 `Agent.state.messages` 是**双写**：`AgentSession._handleAgentEvent` 在 `message_end` 时同时更新内存与文件（`packages/coding-agent/src/core/agent-session.ts:639-719`）。
- `fork(entryId)` 复制文件，`navigateTree(targetId)` 切换当前叶节点并可选生成分支摘要。

此模型已支撑分叉、导航、压缩与分支摘要。不足在于：`id` 是字符串而非单调数字、无全局提交序号、无 `Task/Input` 的形式化状态、事务保证依赖文件追加的原子性。

## 4. 下一代契约：`pi-durable` 的四表模型

`packages/durable/src/types.ts:362` 把日志形式化为四张表，通过一批 `StorageWrite` 原子提交：

### 4.1 四张表

```ts
// packages/durable/src/types.ts:288-297
type StorageWrite =
  | { type:"conversation"; value: ConversationRecord }
  | { type:"entry";        value: EntryRecord }
  | { type:"task";         value: TaskRecord<JsonValue,JsonValue,JsonValue> }
  | { type:"input";        value: Input };

interface Storage {
  commit(writes: StorageWrite[], context: Context): Promise<Seq>; // 原子提交，返回全局序号
  mintId(): Id; // 申请一个全局唯一的单调递增 Id（1 保留给根分支）
  conversation(id, ctx): Promise<ConversationRecord | undefined>;
  scanConversations(cursor, limit, ctx): Promise<Page<ConversationRecord, Cursor>>;
  entry(id, ctx): Promise<{ entry: EntryRecord; commitSeq: Seq } | undefined>;
  findLatestHeadMarker(conversationId, atOrBeforeEntryId?, ctx): Promise<EntryRecord & { head: Id } | undefined>;
  scanEntries(query: EntryQuery, cursor, limit, ctx): Promise<Page<EntryRecord, Cursor>>;
  task / scanTasks / input / inputByRequest / close
}
```

- `Id` 与 `Seq` 都是数字。`Id` 是记录的全局唯一标识，`Seq` 是每次 `commit` 的全局提交序号。
- `EntryRecord`（`types.ts:51-67`）：`{ id, conversationId, kind, model?: Message[], data?: JsonValue, head?: Id, edits?: ContextEdit[], byTaskId? }`。`head` 为“从我开始的新可见范围”，`edits` 可覆盖旧记录的模型消息（`omit` 丢弃或 `replace` 替换）。
- `TaskRecord<I,S,R>`：描述一个可持久化任务的状态（`pending`/`running`/`terminal`）与结果（`completed`/`failed`/`aborted`/`orphaned`/`faulted`），含依赖 `after`、是否后台 `background`、是否请求中止等。
- `Input`：描述一条外部输入的生命周期（`queued` → `placed` → `done` 或 `unanswered`），支持按 `requestId` 去重。
- `DocumentRecord`：描述文档的多版本与分叉策略（按 `session`/`conversation`/`task` 作用域）。

### 4.2 MemoryStorage 的不变量

`packages/durable/src/memory-storage.ts:112` 是参考实现，它强制的不变量也是所有后端必须满足的：

- **原子性**：一批 `writes` 要么全部落盘，要么全部不落，返回同一个 `Seq`。
- **全局唯一**：`conversation` 与 `entry` 的 `id` 不可复用、不可跨表复用；`task` 与 `input` 的可覆盖但不可跨表。
- **深拷贝隔离**：读写均做深拷贝，行为与序列化后端的拥有边界一致。
- **可见范围继承**：`scanEntries` 与 `findLatestHeadMarker` 会沿 `parent` 链回溯，自动合并前缀，`head` 的值即范围下界。

### 4.3 与现役的对照

| 维度 | 现役 `SessionManager` | 新 `pi-durable` |
|---|---|---|
| 标识 | 字符串 `uuidv7` | 数字 `Id`，单调递增，`1` 为根 |
| 提交序 | 无全局序号，依赖文件行序 | 数字 `Seq`，每次 `commit` 递增 |
| 分叉 | 隐含在 `parentId` 链中 | 显式的 `ConversationRecord.parent` |
| 可见范围 | 隐式：当前叶节点 + 最近压缩点 | 显式：`Entry.head` + `ContextEdit[]` |
| 任务与输入 | 无（一等概念是内存中的 Lane） | 一等 `TaskRecord`/`Input` 状态机 |
| 存储 | JSONL 文件 + SQLite | `durable.Storage`（目前仅 `MemoryStorage` 参考实现） |

`0.86.1` 时 `pi-durable` 尚未被 `agent`/`coding-agent` 直接依赖，`agent/harness/pico3` 是实验性参考内核，生产仍走现役路径。

## 5. 具体例子：一次分叉与压缩

```
初始分支 A（根，id=1）
  记录 1: kind="message" model=[user "加端到端用例"]          head=1
  记录 2: kind="message" model=[assistant(Text+ToolCall read)]
  记录 3: kind="message" model=[toolResult read]
  记录 4: kind="message" model=[assistant "已实现，跑测试"]
  // 此时可见范围从记录 1 开始，读取 A 得到 [4,3,2,1]

用户执行“/fork 尝试 WASM 方案”→ 新分支 B { parent:{ conversationId:1, at:4 } }
  记录 5: 分支 B, kind="message" model=[user "用 WASM 重做"]
  记录 6: 分支 B, kind="message" model=[assistant(Text+ToolCall write)]
  // 读取 B 得到 [6,5] + 继承 A 的 [4,3,2,1]

上下文用了 80% → 触发压缩
  记录 7: 分支 B, kind="compaction" head=7, edits=[{target:2, action:"omit"}, ...]
          data={ summary:"已尝试两种方案...", oldLeafId:6, newLeafId:7 }
  // 可见范围从记录 7 开始，后续发给模型的只有 7 之后的记录

切回分支 A → 生成分支摘要
  记录 8: kind="branchSummary" { entriesToSummarize:[5,6], summary:"WASM 分支未合入" }
```

这个例子回答了三个问题：从哪里恢复（`head`）、继承什么（`parent` 链）、压缩后丢什么（`edits` 与 `data.summary`）。

## 6. 为何需要两代

- **现役代回答“能不能用”**：`SessionManager` 已让 `pi --continue` / `fork` / `分支导航` 可用，且与内存状态双写一致。
- **下一代回答“能不能形式化地演进”**：单调 `Id`/`Seq`、原子 `commit`、`Task/Input` 状态机、跨分支的可见范围继承，使 `Harness` 的 `Lane/Drive` 可以被重写为 `durable` 上的纯任务调度（`pico3` 的 `kinds/` 已展示 `collapse/frames/generation` 等任务种类）。

下一章 `04` 将展示 `Harness.Drive` 如何在现役图上驱动状态机，以及它如何逐步向新契约迁移。
