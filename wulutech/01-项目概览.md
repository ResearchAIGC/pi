## 1. 问题：长程编码任务会遇到什么

想象你要让 Agent 在终端里完成一个真实任务：“给这个仓库加一个图像压缩的端到端用例，跑通后改成分辨率自适应”。它需要读文件、写代码、跑测试，持续数十轮对话。很快会撞上四个具体困难：

1. **想试两条路，但历史是一条直线**。比如你想同时尝试“用 WASM 实现”和“用原生库实现”，再择优合并。线性的 `messages[]` 没有分支，只能丢弃重来。
2. **进程一重启，记忆就丢了**。上下文溢出、网络抖动、进程崩溃都会丢状态。没有持久化，会话不可恢复、不可审计。
3. **每接一个新模型就要写一堆 `if`**。自建网关、本地 `llama.cpp`、企业网关都号称“兼容 OpenAI”，但对 `store`、`reasoning_effort`、`thinking` 等字段的支持各不相同。
4. **想加能力就得改内核**。比如你想把 `bash` 放进容器、加一个审计拦截、或给项目加专属命令，如果工具写死在内核，只能 fork。

**Pi 的选择是：不做更聪明的聊天机器人，做一套可被复用的底座（Harness）+ 可被扩展的产品。** 底座解决前两点，扩展与模型抽象解决后两点。

## 2. 解法：四层分工

```
用户
  │
  ├─ 交互层  pi-tui（终端界面，自研差分渲染）
  │          + chord（应用组合运行时，提供插件与 RPC 原语）
  │          + pi-protocol（传输中立的 CBOR 帧，支撑远程）
  │          └─ 效果：本地 TUI 与远程 Client-Server 用同一套事件
  │
  ├─ 产品层  pi-coding-agent（命令 pi，负责把一切粘起来）
  │          └─ 包含 8 个工具、Skills、压缩、配置与信任、三运行模式
  │
  ├─ 底座层  pi-agent-core（单次运行的循环与状态）
  │          + pi-durable（会话的形式化契约，定义图如何存）
  │          └─ 职责：循环、并发、持久化、分支与压缩
  │
  └─ 能力层  pi-ai（统一多模型抽象，30+ Provider × 10 种 Api）
             └─ 特点：按 Api（协议）而非 Provider（厂商）组织，差异用开关消化
```

依赖方向严格向下。只有一条例外：`agent` 通过 `pi-telemetry` 产出可观测的 Span，这是接口依赖而非实现依赖。

## 3. 12 个包的版图（`0.86.1`）

构建顺序（`package.json:16`）：

```
chord → tui → telemetry → ai → durable → agent → session-backends/sqlite-node → protocol → client → server → coding-agent
```

`durable` 在 `0.86.0` 插入到 `ai` 之后、`agent` 之前。这体现了“先定义存储契约，再实现运行时”的顺序。

| Package | npm 名 | 为何要独立成包 | 一句话职责 |
|---|---|---|---|
| `chord` | `@earendil-works/chord` | 应用组合运行时，可被非 Pi 项目复用 | 插件（Facet）+ 复制状态 + RPC |
| `tui` | `@earendil-works/pi-tui` | 自研渲染，比 Ink/Blessed 更快更可控 | 差分渲染 + 布局 + 编辑器/图片/剪贴板 |
| `telemetry` | `@earendil-works/pi-telemetry` | 厂商中立的观测契约，被多包共用 | 定义 Span/Event 的强类型 Schema |
| `ai` | `@earendil-works/pi-ai` | 统一多模型，需独立发版与按需加载 | `Model` / `Message` / `ProviderStreams` / 30+ Provider × 10 Api |
| `durable` | `@earendil-works/pi-durable` | **0.86.0 新增**，会话的形式化契约层 | `Conversation/Entry/Task` + 原子提交 + `MemoryStorage` 参考实现 |
| `agent` | `@earendil-works/pi-agent-core` | 通用 Agent 运行时，可被非编码场景复用 | `Agent` 循环 + `Harness`（Lane/Drive）+ 会话存储 |
| `session-backends/sqlite-node` | `@earendil-works/pi-session-backend-sqlite-node` | 隔离 `node:sqlite` 依赖，按需引入 | `agent` 的 SQLite 存储后端 |
| `protocol` | `@earendil-works/pi-protocol` | 传输中立，可走任意字节流 | `PROTOCOL_VERSION=8` + CBOR 帧 |
| `client` / `server` | `@earendil-works/pi-client` / `pi-server` | 远程会话的传输层 | `PiClient` / `PiServer` + `SessionRouter` |
| `coding-agent` | `@earendil-works/pi-coding-agent` | 产品粘合层 | `AgentSession` + 8 工具 + 扩展 + 三运行模式 + SDK |
| `evals` | `@earendil-works/pi-evals` | 评测集，`private:true` 不发布 | 评测用例与脚本 |

> 顶层 `README.md` 的“7 行精选表”是面向用户的裁剪版；此处补全 12 个 workspaces 的全貌，避免以偏概全。

## 4. 设计哲学

1. **底座大于聊天**。`AgentHarness`（`packages/agent/src/harness/`）把会话、分支、压缩、重试、队列、持久化做成可复用底座；`Agent`（`packages/agent/src/agent.ts:592`）只负责单次运行的循环与事件；`coding-agent` 在此之上做产品化。
2. **会话是一张图**。`Entry { id, head, edits }`（`packages/durable/src/types.ts:51-67`）的追加日志是分支与压缩的唯一真源，适合长程任务。
3. **按协议而非按厂商组织模型**。`pi-ai` 以 `Api`（如 `openai-completions` 等 10 种，`packages/ai/src/types.ts:17-28`）而非 `Provider` 组织能力，网关差异用 `Model.compat` 的 20+ 开关消化，模型目录由 `scripts/generate-models.ts` 生成、禁止手改。
4. **扩展是一等公民**。扩展可注册工具、命令、快捷键、界面，并拦截 `tool_call` 等事件。`0.86.0` 起扩展对提示词与工具的修改会持久化到会话，跨重启与分支保留。
5. **工程化克制**。`AGENTS.md` 约束“无 `any`、无内联导入、仅 erasable TS、依赖精确固定、shrinkwrap 锁定”等；供应链硬化在同类 Agent 中少见。

## 5. 如何构建与校验

- **构建**：`npm run build`（按上表顺序）或 `build:offline`（复用已抓取的模型数据，不触网）。
- **校验**：`npm run check` 会依次执行格式、依赖、导入、类型等 8 项检查（`package.json:21`），需全部通过才能提交。
- **测试**：`./test.sh`（跳过需 API Key 的端到端用例）；单文件可用 `node $(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js --run test/specific.test.ts`；`packages/tui` 用 `node:test`。
- **运行**：`./pi-test.sh` 可从源码直接运行 `pi`，无需安装。
- **发布**：`npm version --workspaces` 同步改版本 + `scripts/sync-versions.js` + `scripts/publish.mjs`；二进制用 `scripts/build-binaries.sh --offline-model-data` 产出。
