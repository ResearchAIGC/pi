# 08 — 扩展与工程化：自扩展如何落地、供应链如何硬化

> 源码锚点：`packages/coding-agent/src/core/extensions/types.ts:1500` / `packages/coding-agent/src/core/extensions/{loader,runner,wrapper}.ts` / `AGENTS.md` / `package.json:21`

---

## 1. 为什么扩展是一等公民

如果“容器化、审计、本地模型、项目专属命令”都要改内核代码，Pi 的演进会被分支撕裂。Pi 的约束是：**所有“策略”由扩展实现，内核保持中立**。例如：

- 危险命令 `rm -rf /` 由扩展的 `tool_call` 拦截，而非内核硬编码。
- 容器化（Gondolin）由扩展覆写 `BashOperations`，而非在 `tools/bash.ts` 中分支。
- 提示词注入由扩展的 `before_agent_start` 链式修改，而非写死在 `buildSystemPrompt`。

本章先讲扩展如何发现、执行与注册，再讲保障这套机制可演进的工程化约束。

## 2. 发现与加载（`extensions/loader.ts`）

### 2.1 发现路径（按优先级）

1. CLI 显式 `-e <path>` 指定的路径
2. `~/.pi/agent/extensions/*`（全局，每个子目录一个扩展，含 `package.json`）
3. 项目内 `.pi/extensions/*`（需项目已信任）
4. `packages/coding-agent/examples/extensions/*`（示例：`gondolin`、`custom-provider` 等）

扫描后经 `ResourceLoader`（`core/resource-loader.ts`）去重与校验，并受 `ProjectTrustStore`（`~/.pi/agent/trust.json`）的信任门控。

### 2.2 加载

```ts
loadExtensions(factories: ExtensionFactory[]) → { runner: ExtensionRunner, diagnostics }
loadExtensionFromFactory(factory, sourceInfo) → { extension, diagnostics }
```

一个扩展模块的默认导出可以是：

- `ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>`（函数式，推荐）
- `Extension = { name, setup(pi) }`（对象式）
- `InlineExtension`（内联工具，用于 SDK 的 `customTools`）

`SourceInfo { path, packageName?, version? }` 用于诊断与热重载；`0.86` 起编译器延迟到首次加载文件扩展时才初始化，以降低 SDK 的基线成本。

### 2.3 SDK 内联

通过 `createAgentSession({ customTools: [defineTool({...})] })`，可不走文件扫描直接注入工具，再与扩展工具合并。

## 3. ExtensionAPI（`extensions/types.ts:1252-1461`）

### 3.1 事件订阅

扩展通过 `pi.on(event, handler)` 订阅 30 多个生命周期事件。按用途可分为四组：

**会话与资源**：`project_trust`、`resources_discover`、`session_start`、`session_before_switch`、`session_before_compact`、`session_compact_failed`。

**输入与模型**：`input`（可改写或接管输入）、`context`（每次调模型前注入消息）、`before_provider_request` / `before_provider_headers`（改写请求）、`model_select`、`cache_warming_decision`（`0.86` 新增）。

**Agent 循环**：`before_agent_start`（可注入上下文或改写提示词，`0.86` 起会持久化）、`agent_start` / `agent_end` / `agent_settled`、`turn_start` / `turn_end`、`message_start` / `message_update` / `message_end`。

**工具与命令**：`tool_call`（可拦截与改写入参）、`tool_result`（可改写出参）、`tool_execution_start` / `update` / `end`、`user_bash`（接管 `!` 命令，`0.86` 起失败时不再降级到本地）。

```ts
pi.on("tool_call", (e) => {
  if (e.toolName === "bash" && e.input.command.includes("rm -rf /"))
    return { block: true, reason: "拒绝危险命令" };
});
pi.on("before_agent_start", (e, ctx) => {
  // 可注入 CustomMessage 或改写 systemPrompt
});
```

所有处理器签名均为 `(event, ctx: ExtensionContext) => Promise<R|void>`。`pi.on()` 在 `0.86.0` 新增返回 `unsubscribe` 函数，`dispatch` 期间的增删仅对后续生效。

### 3.2 注册

```ts
pi.registerTool({ name, description, parameters: Type.Object({...}), execute, renderCall, renderResult })
pi.registerCommand(name, { description, handler: (args, ctx) => void })
pi.registerShortcut(keyId, { description, handler: (ctx) => void })  // 如 "ctrl+g"
pi.registerFlag(name, { type: "boolean"|"string", description, default })
pi.registerMessageRenderer(customType, renderer) // 自定义消息渲染
pi.registerProvider(name, { baseUrl, api, models }) // 注册新模型厂商
```

工具的 `execute` 会收到 `(toolCallId, params, signal?, onUpdate, ctx)`，可通过 `onUpdate` 推送中间进度。

### 3.3 上下文

- **ExtensionContext**（每次事件触发时创建）：提供 `ui`（界面）、`mode`（`tui`/`rpc`/`print`）、`cwd`、`sessionManager`（只读）、`model` / `thinkingLevel`、`isIdle()`、`signal`、`abort()`、`getContextUsage()`、`compact()` 等。按“只读信息 / 操作 / 界面”三组组织，便于查阅。
- **ExtensionCommandContext**（命令处理器额外获得）：额外提供 `waitForIdle()`、`newSession()`、`fork()`、`navigateTree()` 等会替换会话的方法。涉及会话替换的方法需在 `withSession` 回调中完成后续工作，否则旧上下文会被标记为过期。
- **模型直调**：`0.86.0` 新增 `ctx.modelRegistry.stream()`，扩展可直接调模型（走已配置的厂商与鉴权）。

### 3.4 界面能力（`ExtensionUIContext`）

```ts
select(title, options) → Promise<string|undefined>  // 选择器
confirm(title, message) → Promise<boolean>           // 确认框
input(title, placeholder) → Promise<string|undefined> // 输入框
notify(message, type?)                              // 通知
setStatus / setWorkingMessage / setWidget           // 状态条与挂件
setFooter / setHeader                               // 页脚与页眉
custom<T>(factory) → Promise<T>                     // 挂载任意 TUI 组件
setEditorComponent(factory)                         // 替换编辑器
```

`custom` 是最灵活的界面能力，允许扩展挂载任意组件，并通过 `OverlayHandle` 控制显隐。

## 4. Runner（`extensions/runner.ts`）

`ExtensionRunner` 是扩展的执行引擎：

- 维护 `handlers`（事件处理器）与 `tools` / `commands` / `shortcuts` 等注册表。
- `emit(event)` 按注册顺序 `await` 每个处理器，捕获异常后上报（`emitError`），单扩展异常不影响其他扩展。
- `emitToolCall` 支持入参的**就地改写**：多个 `tool_call` 处理器依次改同一个对象；`block` 为“任一拦截即拦截”。
- `emitToolResult` / `emitMessageEnd` / `emitBeforeAgentStart` 支持返回值覆盖，后者会链式合并多扩展对提示词的修改（`0.86` 起以 `SystemMessage.sections` 持久化）。

**关键不变量**：扩展异常永不崩溃主流程，仅产出 `handler_error` 并继续；`user_bash` 在 `0.86` 改为失败时直接终止，不再降级到本地执行。

## 5. 典型扩展

### 5.1 Gondolin（容器化）

`examples/extensions/gondolin`：将 `read` / `write` / `bash` 等操作的底层实现覆写为“经 QEMU micro-VM 执行”，并将 `!` 命令路由到虚拟机；`session_start` 时挂载 `cwd → /workspace`。

### 5.2 Custom Provider（自定义模型）

```ts
export default function(pi) {
  pi.registerProvider("my-provider", {
    baseUrl: "https://...",
    api: "anthropic-messages"|"openai-completions",
    models: [{ id, name, reasoning, input, cost, contextWindow, maxTokens, compat }],
  });
}
```

`llama` 扩展还展示了如何拦截模型响应、对接本地 `llama.cpp`。

### 5.3 拦截式审计

```ts
export default function(pi) {
  pi.on("tool_call", (e) => {
    if (e.toolName === "bash" && e.input.command.includes("rm -rf /"))
      return { block: true, reason: "拒绝危险命令" };
  });
  pi.on("tool_result", (e) => {
    e.content = [{ type:"text", text: "[已审计] " + contentText(e.content) }];
  });
}
```

## 6. 工程化与供应链硬化

### 6.1 提交门禁（`AGENTS.md` + `package.json:21`）

每次代码修改后必须执行 `npm run check`（完整输出，不可截断），全部通过才能提交。`check` 包含 8 项：

```
biome check --write --error-on-warnings  格式与 lint
check:pinned-deps                        外部依赖必须精确固定版本
check:runtime-deps                       运行时依赖图校验
check:ts-imports                         禁止越界与内联导入
check:entry-graphs                       入口图校验
check:shrinkwrap / check:install-lock    锁定文件与 lockfile 一致
tsgo --noEmit                            类型检查（TS 原生预览版）
check:browser-smoke                      浏览器冒烟
```

其他约束：不可自动 `npm run build` / `npm test`（除非用户要求）；不可全量 `vitest`（含端到端用例），非端到端用 `./test.sh`，`tui` 用 `node:test`。

### 6.2 Monorepo 协作

- 多个 pi 会话可能同时在同一目录修改不同文件，禁止 `git reset --hard` / `git clean -fd` / `git stash` / `git add .` 等会覆盖他人工作的命令；提交时仅 `git add <路径>` 精确指定，先 `git status` 确认。
- `husky` 预提交钩子含 lockfile 保护：需 `PI_ALLOW_LOCKFILE_CHANGE=1` 才能提交 lockfile 变更。

### 6.3 代码风格

- 无 `any`（除非绝对必要）、单调用点辅助函数内联、查 `node_modules` 而非猜外部 API。
- 无内联 `import()`，仅顶层导入。
- `packages/*/src` 仅 `erasable TS`（`tsconfig.base.json` strip-only）：禁用 `enum`、`namespace` 等需发射的语法。
- 新增快捷键必须加入默认绑定，而非硬编码匹配。
- `models.generated.ts` 禁止手改，仅通过 `generate-models.ts` 重新生成。

### 6.4 依赖与供应链（`README.md:77-90`）

| 措施 | 实现 | 目的 |
|---|---|---|
| 精确固定 | `.npmrc: save-exact=true` + `check:pinned-deps` | 防止版本漂移 |
| 发布延迟 | `.npmrc: min-release-age=2` | 避开同日恶意发布 |
| Lockfile 为真源 | `package-lock.json` + 预提交拦截 | 变更可审计 |
| Shrinkwrap | `packages/coding-agent/npm-shrinkwrap.json` | 消费者锁定传递依赖 |
| Install lock | `packages/coding-agent/install-lock/` | 安装器锁定 |
| 禁止生命周期脚本 | `--ignore-scripts` | 防止投毒 |
| 脚本白名单 | `generate-coding-agent-shrinkwrap.mjs` 内显式白名单 | 防止隐式脚本植入 |
| 定期审计 | GitHub 定时任务 `npm audit` | 持续审计 |
| 本地发布冒烟 | `npm run release:local`（隔离安装验证） | 发布前真实验证 |
| `undici` 强审 | 更新时必须读 changelog | 敏感网络栈 |

本地用 `npm install --ignore-scripts`，CI 用 `npm ci --ignore-scripts`；需刷新 lockfile 时用 `npm install --package-lock-only --ignore-scripts`。

### 6.5 测试与发布

- **脚本自检**：`node --test scripts/*.test.mjs`。
- **Workspace 测试**：`npm run test --workspaces --if-present`；便捷脚本 `./test.sh`（全量非端到端）、`./mini-test.sh`、`./pi-test.sh`。
- **回归规范**：修复 issue 时加 `// fixes #<number>` 注释，提交信息写 `fixes #<number>` 自动关 issue。
- **发布**：`version:patch|minor|major → sync-versions.js → npm install --package-lock-only`；二进制用 `scripts/build-binaries.sh --offline-model-data` 产出。

## 7. 已知局限与演进（`0.86.1` 时）

| 类别 | 现象 | 影响 |
|---|---|---|
| 硬件失效 | 存储的事务假定底层存储原子性，极端硬件失效未覆盖 | 会话错乱需手动修复 |
| 模型截断 | 截断时整批工具被标记失败 | 可能增加重试开销 |
| 扩展隔离 | 扩展与主进程同线程，异常仅隔离到事件 | 恶意扩展可直接访问文件与进程 |
| 全量检查成本 | 8 项检查在大型变更时耗时 | 可考虑增量检查 |
| 模型目录漂移 | `models.generated.ts` 需定期刷新，离线构建可能落后 | 应提示过期时间 |

**近期（P0）**：补齐 `Harness.watchSession`、离线模型过期提示、`parallel` 的可观测性。

**中期（P1）**：`SamplingParams` 分型、`pi-durable` 的 SQLite 适配、`pico3` 向 `durable` 的迁移。

**长期（P2）**：声明式权限策略（类似 Codex 的 `ask`/`auto`）、压缩可回滚、协议版本协商、扩展的 `worker_thread` 沙箱。

## 8. 一句话总结

> Pi 用 **Harness（图结构的持久化会话）+ pi-ai（协议中立的模型抽象）+ 自扩展（TypeBox 工具与 30+ 事件）+ 自研 TUI（差分渲染）** 四件套，把“编码 Agent”从一次性聊天做成了可持久化、可分支、可观测、可被无限扩展的终端操作系统；工程侧以精确固定、锁定与全量门禁保障供应链与质量。其最值得借鉴的是“会话即图 + 扩展即一等公民”的组合。
