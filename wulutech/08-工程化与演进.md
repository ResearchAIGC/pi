## 1. 开发工作流

### 1.1 提交门禁

`AGENTS.md` 规定：

- **每次代码修改后必跑** `npm run check`（完整输出，不可 `tail`），修复全部 `error/warning/info` 后方可提交。
- `check` 的构成（`package.json:21`）：

```
biome check --write --error-on-warnings .    # lint + format
+ check:pinned-deps                          # 外部依赖必须 pinned exact
+ check:runtime-deps                         # 运行时依赖图校验
+ check:ts-imports                           # 禁止相对导入越界 / 内联导入
+ check:entry-graphs                         # 入口图校验
+ check:shrinkwrap / check:install-lock      # shrinkwrap / install-lock 与 lockfile 一致
+ tsgo --noEmit                              # 类型检查（tsgo 为 TS native preview）
+ check:browser-smoke                        # 浏览器冒烟
```

- **不可自动** `npm run build` / `npm test`，除非用户显式要求。
- **不可全量 vitest**：含 e2e（需 provider/auth），非 e2e 需 `./test.sh`；TUI 用 `node:test`；单文件 `node $(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js --run test/specific.test.ts`。
- 修改单测文件后需立即运行并迭代至通过。

### 1.2 Monorepo 协作

- `AGENTS.md`：“多个 pi session 可能同时在同一 cwd 修改不同文件，`git reset --hard` / `git checkout .` / `git clean -fd` / `git stash` / `git add -A` / `git add .` / `git commit --no-verify` 禁止；提交仅 `git add <path1> <path2>` 精确路径；先 `git status` 确认仅含本 session 改动。”
- `husky` 预提交钩子含 lockfile 保护：`PI_ALLOW_LOCKFILE_CHANGE=1` 方可提交 lockfile 变更。

### 1.3 代码风格

- 无 `any`（除非绝对必要）、单调用点辅助函数内联、查 `node_modules` 而非猜外部 API 类型。
- 无内联 `import()` / `import("pkg").Type`，仅顶层导入。
- `packages/*/src` 与 `packages/coding-agent/examples` 仅 erasable TS（`tsconfig.base.json` 的 strip-only 模式）：禁 `enum`/`namespace`/`import =`/`export =`/参数属性等需 emit 的语法。
- 禁硬编码 `matchesKey(keyData, "ctrl+x")`，新增快捷键必须加入 `DEFAULT_EDITOR_KEYBINDINGS` / `DEFAULT_APP_KEYBINDINGS`。
- `models.generated.ts` 禁手改，仅改 `generate-models.ts` 后重生成。

### 1.4 变更日志

`packages/*/CHANGELOG.md` 的 `## [Unreleased]` 下分 `Breaking Changes / Added / Changed / Fixed / Removed`，新条目追加到对应 subsection；已发布版本不可改；`main` 分支外不写 changelog。

## 2. 依赖与供应链硬化

`README.md:77-90` + `scripts/*` 共同构成供应链防线：

| 措施 | 实现 | 目的 |
|---|---|---|
| **Exact pin** | `.npmrc: save-exact=true` + `check:pinned-deps` | 防 semver 漂移 |
| **min-release-age** | `.npmrc: min-release-age=2` | 避开同日恶意发布 |
| **Lockfile 为真源** | `package-lock.json` + pre-commit 拦截 + `PI_ALLOW_LOCKFILE_CHANGE=1` | 变更可审计 |
| **Shrinkwrap** | `packages/coding-agent/npm-shrinkwrap.json`（`generate-coding-agent-shrinkwrap.mjs`）+ `check:shrinkwrap` | 消费者安装时锁定传递依赖 |
| **Install lock** | `packages/coding-agent/install-lock/` + `generate-coding-agent-install-lock.mjs` | 安装器/更新器锁定 |
| **`--ignore-scripts`** | `.npmrc` / CI `npm ci --ignore-scripts` / `pi update --self --ignore-scripts` | 防生命周期投毒 |
| **Lifecycle allowlist** | `generate-coding-agent-shrinkwrap.mjs` 内显式 allowlist，新含脚本依赖需评审后加入 | 防隐式脚本植入 |
| **定期审计** | GitHub Scheduled Workflow：`npm audit --omit=dev` + `npm audit signatures --omit=dev` | 持续审计 |
| **本地发布冒烟** | `npm run release:local`（build→pack→隔离 npm/Bun 安装） | 发布前真实安装验证 |
| **undici 强审** | 更新 `undici` 必须读 changelog 并评估功能影响 | 该依赖为敏感网络栈 |

依赖 Hydrate：本地 `npm install --ignore-scripts`，CI `npm ci --ignore-scripts`；需刷新 lockfile 时 `npm install --package-lock-only --ignore-scripts`。

## 3. 测试与质量

### 3.1 测试分层

- **脚本自检**：`npm run test:scripts` → `node --test scripts/*.test.mjs`（`package.json:40`）。
- **Workspace 测试**：`npm run test --workspaces --if-present`（`vitest` / `node:test` 按包而异）。
- **便捷脚本**：`./test.sh`（全 non-e2e）、`./mini-test.sh`（最小集）、`./pi-test.sh`（从源码跑 `pi`）。
- **Harness 专项**：`packages/coding-agent/test/suite/harness.ts` + faux provider（`packages/ai/src/providers/faux.ts`），无真实 Provider/Key/计费。

### 3.2 回归规范

为 GitHub issue 修 bug 时，需在回归测试旁加注释 `// fixes #<number>`（AGENTS.md 隐含于 CONTRIBUTING）。发布时 `fixes #<number>` / `closes #<number>` 关键字自动关 issue，多 issue 需每条重复关键字（`closes #1, closes #2`，共享关键字仅关首条）。

### 3.3 类型与格式

`biome.json` 统一 lint/format，`tsgo`（TS native preview `7.0.0-dev`）做无发射类型检查，`eslint` 未使用。

## 5. 安全与部署（`SECURITY.md` / `docs/containerization.md` / `docs/security.md`）

### 5.1 威胁模型

`README.md:41-48` 明确：**Pi 默认无权限隔离**，以启动用户的全部权限运行文件/进程/网络；需边界时由用户自行容器化/沙箱化。

### 5.2 四种容器化模式

| 模式 | 隔离对象 | 适用 | Key 归属 |
|---|---|---|---|
| **Gondolin 扩展** | 工具 + `!` 命令（micro-VM） | 本地 VM 隔离且 key 留 host | host |
| **Plain Docker** | 整个 `pi` 进程（容器）| 简单本地隔离 | container |
| **OpenShell** | 整个 `pi` 进程（策略沙箱）| 托管沙箱 | gateway |
| **Docker Sandboxes** | 整个 `pi` 进程（`sbx`）| key 留 host 的托管沙箱 | host |

扩展随 `pi` 进程走：host Pi + 工具路由扩展时，其他自定义扩展工具仍在 host 执行，除非自行委托。

### 5.3 信任决策

`.pi/agent/trust.json` + `project_trust` 扩展事件：初次在某 `cwd` 发现项目级扩展/skills/prompts 时弹确认（`yes/no/undecided` + `remember`），可由扩展自定义问询 UI。

## 6. 已知的局限与风险

| 类别 | 现象 | 影响 |
|---|---|---|
| 硬件失效 | Harness 的 `Storage` 事务与 `MutationLine` 假定底层存储（SQLite/文件）原子性，极端硬件失效未覆盖 | 会话错乱需手动修复 |
| 模型截断 | `length` 截断被视为“全部工具调用不可信”并整体失败重试，对“部分可执行”的截断场景浪费 token | 应提供可选“部分执行”策略 |
| 扩展隔离 | 扩展与主进程同线程，异常仅 `handler_error` 隔离；恶意扩展可直接 `fs`/`process` | 需信任模型或后续 worker 隔离 |
| 全量 `check` 成本 | `tsgo` + `biome --write` + 5 项脚本校验在大型变更时耗时显著 | 可考虑增量 check |
| 模型目录漂移 | `models.generated.ts` 需定期 `generate:models`，离线 `build:offline` 可能落后 | 应显式告警目录过期时间 |

## 7. 演进建议（按优先级）

### P0 — 近期可做，收益明确

1. **Harness `watchSession` 实现**（`harness.ts:305` 仍 `SliceNotImplemented`）：补齐会话级订阅，支撑 Dashboard/多客户端观察。
2. **扩展 Worker 隔离（可选）**：为不信任扩展提供 `worker_thread` 沙箱，`ExtensionAPI` 代理到宿主，失败仅杀 worker。
3. **`--offline-model-data` 过期提示**：二进制构建与启动时若模型目录超 N 天未刷新，打印 warning 并指引 `npm run generate:models`。

### P1 — 架构增强

4. **结构化 `SamplingParams` 类型**：当前 `samplingParams: Record<string,unknown>`，可为 `openai`/`anthropic`/`google` 分型，减少 provider 间透传错配。
5. **工具并发策略的可观察性**：为 `parallel` 模式的“准备串行→执行并发”增加 `HarnessSpan` 事件，便于定位慢工具。
6. **Session 存储可观测性**：`Storage` 层增加 `TelemetryContext` 透传，`SessionManager` append 失败时产出结构化 span（含 `entryType`/`seq`）。

### P2 — 长期

7. **声明式权限策略**：在 `SettingsManager` 增加 `permissions: { allow: { bash:[...], write:[...] }, deny:[...] }`，由 `before_tool` 统一执行，替代各扩展散落的 `block` 逻辑，并支持 `--permission-mode`（如 Codex 的 `ask`/`auto`）。
8. **会话压缩的可回滚**：`CompactionEntry` 增加 `prevLeafId`，`SessionManager.navigateTree` 支持“一键撤销最近压缩”。
9. **Protocol 版本协商的兼容层**：当前 `PROTOCOL_VERSION=8` 单版本，客户端 `ClientHello.version` 未做兼容协商；后续可加 `minVersion/maxVersion` 协商与旧客户端优雅降级。

## 9. 一句话总结

> Pi 用 **Harness（ durable lane + session DAG ）+ pi-ai（ provider-agnostic model ）+ 自扩展（ TypeBox tool + 30+ events ）+ 自研 TUI（ diff render ）** 四件套，把“编码 Agent”从一次性聊天做成了可持久化、可分支、可观测、可被用户无限扩展的**终端操作系统**；工程侧以 **exact pin + shrinkwrap + --ignore-scripts + 全量 check 门禁** 保障供应链与质量。其最值得借鉴的是“会话即 DAG + 扩展即一等公民”的组合。
