# 05 — AI 抽象层：如何消化 30+ 模型的差异

> 源码锚点：`packages/ai/src/types.ts:1024` / `packages/ai/src/providers/` / `packages/ai/src/api/` / `packages/ai/src/models.generated.ts`

---

## 1. 为什么不能按厂商组织代码

“接入 30 个模型”的朴素做法是写一串 `if (provider === "openai") ... else if (provider === "anthropic")`，但很快会失控：

- **同一厂商有多个协议**：OpenAI 同时提供 `openai-completions`（Chat Completions）与 `openai-responses`（Responses API），参数与能力不同。
- **不同厂商用同一协议**：十几个“兼容 OpenAI”的网关（DeepSeek、Qwen、Together 等）都走 `openai-completions`，但对 `store`、`reasoning_effort`、`thinking` 等字段的支持各不相同。
- **模型目录在变**：厂商的模型列表、价格、上下文窗口需定期从上游拉取，不能手写。

Pi 的做法是：**按 Api（协议）而非 Provider（厂商）组织能力，用兼容开关消化差异，用生成脚本保证目录新鲜。**

## 2. 核心类型

### 2.1 Api 与 Provider（`packages/ai/src/types.ts:17-77`）

```ts
type KnownApi = "openai-completions" | "openai-responses" | "azure-openai-responses"
              | "openai-codex-responses" | "anthropic-messages" | "bedrock-converse-stream"
              | "google-generative-ai" | "google-vertex" | "mistral-conversations"
              | "pi-messages";
type Api = KnownApi | (string & {}); // 开放枚举，允许自定义 Api

type KnownProvider = "anthropic" | "openai" | "google" | "deepseek" | "openrouter"
                   | "qwen-token-plan" | "xai" | "groq" | "cerebras" | ... ; // 30+ 个
```

可以这样理解：`Api` 是“协议方言”，`Provider` 是“厂商”。一个厂商可能说多种方言（如 OpenAI 同时支持两种 Api），多种厂商也可能说同一种方言（如十几个网关都说 `openai-completions`）。

### 2.2 Model

`Model`（`types.ts:982-1017`）按四组组织字段：

```ts
interface Model<TApi extends Api> {
  // 标识：是谁、说哪种方言
  id, name: string; api: TApi; provider: ProviderId; baseUrl: string;
  // 能力：是否支持推理、输入类型、图片限制
  reasoning: boolean; input: ("text"|"image")[]; inputLimits?: ModelInputLimits;
  thinkingLevelMap?: ThinkingLevelMap; // Pi 的思考等级如何映射到厂商的具体值
  // 计费与上下文
  cost: ModelCost; // 含分层计费 tiers
  promptCache?: ModelPromptCache; // 缓存寿命（秒），用于决定是否预热
  contextWindow: number; maxTokens: number;
  // 透传与兼容
  samplingParams?: Record<string, unknown>; // top_p 等，按 key 合并
  headers?: Record<string,string>;
  compat?: OpenAICompletionsCompat | ...; // 见第 4 节
}
```

`ThinkingLevel` 有 `off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max` 七档，后两档仅部分模型支持，需通过 `thinkingLevelMap` 检测。

### 2.3 消息与上下文

消息分四种（`types.ts:491-553`）：

- `SystemMessage`：首条是基础提示词，后续的 `sections` 可替换提示词的某个命名段落，`toolsAdded/toolsRemoved` 可增删工具。`getCurrentSystemPrompt(messages)` 重放所有 `system` 消息即可得到当前提示词（`0.86` 引入的持久化机制）。
- `UserMessage` / `AssistantMessage` / `ToolResultMessage`：用户输入、模型回复、工具结果。工具参数用 `TypeBox` 定义，`validateToolArguments()` 在执行前校验。
- `Usage` 记录 `input`/`output`/`cacheRead`/`cacheWrite` 等 token 数与费用。
- `DeferredHandle` 用于异步长任务的轮询句柄。

### 2.4 选项与回调

```ts
interface ProviderRequestOptions { signal?, apiKey?, fetch?, env?, headers?, timeoutMs?, ... }
interface StreamOptions extends ProviderRequestOptions { temperature?, maxTokens?, transport?, cacheRetention?, sessionId? }
interface SimpleStreamOptions extends StreamOptions { toolChoice?, reasoning?, deferred?, thinkingBudgets? }
```

- `getApiKey(provider)` 允许每次调模型前动态刷新短生命周期 token（如 GitHub Copilot 的 OAuth 与 `0.86.1` 新增的 Meta Muse）。
- `onPayload` 可在发送前改写请求体，供扩展或网关注入逻辑。

### 2.5 事件流协议（`types.ts:631-668`）

模型以事件流的形式流式返回：

```ts
type AssistantMessageEvent =
  | {type:"start"; partial}              // 开始，携带空的初始消息
  | {type:"text_start|delta|end"; ...}   // 文本块：开始、增量、结束
  | {type:"thinking_start|delta|end"; ...} // 思考块
  | {type:"toolcall_start|delta|end"; ...} // 工具调用：参数在 start 时不完整
  | {type:"done"; reason; message}       // 正常结束
  | {type:"error"; reason; error}        // 异常结束
```

约束：必先 `start`，以 `done` 或 `error` 结束，文本块在 `start` 时为空、仅通过 `delta` 增长。`AssistantMessageEventStream` 是 `EventStream<AssistantMessageEvent, AssistantMessage>`，`response.result()` 可得最终消息。

## 3. Provider 与 Api 如何协作

```
providers/<provider>.ts  例如 anthropic.ts、openai.ts
    ↓ 创建 Provider 实例，绑定模型列表、鉴权、流式实现
api/<api>.ts             例如 anthropic-messages.ts、openai-completions.ts
    ↓ 实现 ProviderStreams { stream, streamSimple, fetchDeferred? }
    ↓ 发起 HTTP(S)/WebSocket，产出事件流
```

`providers/all.ts` 导出全量列表，`api/lazy.ts` 的 `lazyApi()` 按需加载以避免一次性打包所有实现。`src/index.ts` 仅导出核心类型，无副作用。

目前支持的 Provider（`types.ts:35-76`）包括 `anthropic`、`openai`、`google`、`deepseek`、`openrouter`、`qwen`、`zai`、`meta`（`0.86.1` 新增）等 30 多个。

## 4. 兼容开关：如何消化“兼容但有差异”

以 `OpenAICompletionsCompat`（`types.ts:674-751`）为例，它有 20 多个开关，每个开关对应一个具体的网关差异：

- **字段支持**：`supportsStore`（是否支持 `store` 字段）、`supportsReasoningEffort`（是否支持 `reasoning_effort`）、`supportsUsageInStreaming`（流式是否返回用量）。
- **字段位置**：`maxTokensField`（`max_tokens` 还是 `max_completion_tokens`）、`requiresToolResultName`（工具结果是否必须带 `name`）。
- **思考块编码**：`thinkingFormat` 有 6 种取值（`openai` / `deepseek` / `together` 等），对应不同网关对思考过程的编码方式，另有 `chatTemplateKwargs` 透传自定义参数。
- **其他**：`supportsStrictMode`（是否支持严格工具约束）、`cacheControlFormat`（缓存控制格式）、`vllmPriority`（vLLM 调度优先级）等。

举个具体例子：`Cerebras` 曾被误标为支持 `strict` 工具，导致混用严格与非严格工具时报 HTTP 400（`#9804`）。这类问题通过开关的精确配置来避免，而无需改上层代码。

Anthropic 侧也有类似开关，如 `supportsCacheControlOnTools`、`forceAdaptiveThinking`、`allowedFallbackModels` 等（`types.ts:778-840`）。正是这套系统化的开关，使 Pi 能在不改上层的情况下接入大量网关与自建服务。

## 5. 模型发现与目录

- `Models`：内存中的模型集合，提供 `find(provider, id)` / `list()` 等查询。
- `ModelsStore`：负责持久化与刷新（`hydrateModelData` / `checkModelData`），数据来源是 `models.generated.ts`——它由 `scripts/generate-models.ts` 从各厂商 API 拉取生成，**禁止手改**。
- `model-catalog`：发布用的聚合产物（`scripts/generate-model-catalog`）。
- 图片模型：`image-models.generated.ts` 等单独管理图片生成相关的类型。
- `0.86.0` 新增 `inputLimits.images.resize`（按模型的图片缩放配置）与 `Radius` 离线目录；`0.86.1` 新增 `promptCache` 寿命元数据（供缓存预热判断）。

---

## 6. 鉴权

- 支持 API Key、OAuth（Device Code / PKCE）等多种方式（`AuthContext` / `CredentialStore`）。
- `env-api-keys.ts` 从环境变量解析 `ANTHROPIC_API_KEY` 等约定 key。
- 扩展可通过 `compat/extension-oauth-types.ts` 注册自定义 OAuth 厂商（如 `llama` 扩展注册 Hugging Face）。
- `meta` Provider（`0.86.1`）：`/login meta` 的 Muse OAuth 与 `META_API_KEY` 直连，均支持自动刷新。
- `getApiKey(provider)` 允许每次请求前异步刷新；失败时上层会提示 `/login <provider>`。

## 7. 与 Agent 的集成

| 职责 | 在 `pi-ai` 中 | 在 `agent` 中 |
|---|---|---|
| 统一消息与工具 | `Message` / `Tool` / `TranscriptContext` | `AgentMessage` / `AgentTool` / `AgentContext` |
| 统一模型 | `Model<TApi>` | `Agent.state.model` |
| 统一流 | `EventStream` | `StreamFn` |
| 统一鉴权 | `auth/*` + `Models` | `Agent.getApiKey` / `ModelRuntime.getAuth` |
| 错误编码 | `stopReason:"error"` | 循环检测后结束轮次 |

关键约束：`StreamFn` 永不抛异常，失败编码为流中的 `error` 事件；`samplingParams` 按 key 合并，模型默认值可被单次请求的覆盖。

## 8. 如何扩展

- **加新厂商**：实现 `ProviderStreams`（`stream` / `streamSimple`），在 `providers/<name>.ts` 注册工厂与模型列表，运行 `npm run generate:models` 刷新目录。
- **加新协议**：新增 `api/<name>.ts` 实现 `ProviderStreams`，在 `types.ts` 的 `KnownApi` 中注册。
- **自定义采样**：通过 `samplingParams` 与 `chat_template_kwargs` 透传，适配 `llama.cpp` / `vLLM` / `SGLang` 等。
