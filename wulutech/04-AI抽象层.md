# 04 — AI 抽象层（pi-ai）

> 源码：`packages/ai/src/`（约 40k 行，含生成文件）
> 核心：`types.ts` / `models.ts` / `providers/*.ts` / `api/*.ts` / `auth/*` / `models.generated.ts`

---

## 1. 设计目标

`pi-ai` 要解决的核心矛盾：**30+ Provider × 10 种 API × 动态模型目录 × 多种鉴权方式**，却要对上层暴露 **单一、类型安全、可 tree-shake** 的 `Model` + `Context` + `stream()` 契约。

关键约束（`src/index.ts:4-8` 注释）：

> `index.ts` 仅导出 core（无副作用）；Provider 工厂在 `providers/*`，API 实现在 `api/*`，旧全局 API 在 `compat`。避免一次性打包所有 Provider。

## 2. 核心类型（`types.ts` — 881 行）

### 2.1 Api / Provider

```ts
type KnownApi = "openai-completions" | "mistral-conversations" | "openai-responses"
              | "azure-openai-responses" | "openai-codex-responses" | "anthropic-messages"
              | "bedrock-converse-stream" | "google-generative-ai" | "google-vertex" | "pi-messages";
type Api = KnownApi | (string & {});  // 开放枚举，允许自定义 API

type KnownProvider = "anthropic" | "openai" | "google" | "deepseek" | "openrouter" | ... ; // 30+
type ProviderId = KnownProvider | string;
```

`Api` 是**协议维度**，`Provider` 是**厂商维度**；一个 Provider 可能通过多个 Api 暴露模型（如 OpenAI 同时有 `openai-completions` 与 `openai-responses`）。

### 2.2 Model

```ts
interface Model<TApi extends Api> {
  id, name: string;
  api: TApi; provider: ProviderId; baseUrl: string;
  reasoning: boolean;
  thinkingLevelMap?: ThinkingLevelMap;  // pi level → provider value，null 表示不支持
  input: ("text"|"image")[]; cost: ModelCost; contextWindow: number; maxTokens: number;
  samplingParams?: Record<string, unknown>; // top_p / top_k 等，按 key 合并
  headers?: Record<string,string>;
  compat?: OpenAICompletionsCompat | OpenAIResponsesCompat | AnthropicMessagesCompat | BedrockCompat;
}
```

`ModelCost` 含 `tiers`（按输入 token 阈值分层计费，最高匹配阈值对全请求生效）。`compat` 是**按 Api 细分的兼容性开关**（如 OpenAI 的 `supportsStore` / `supportsReasoningEffort` / `requiresThinkingAsText`，Anthropic 的 `supportsCacheControlOnTools` / `allowedFallbackModels` 等，`types.ts:568-739`），用于适配各 Provider 的“类 OpenAI/Anthropic 但有差异”实现。

### 2.3 Context / Message

见 `02-架构总览.md §2.1`，不再重复。补充：

- `Tool.parameters` 为 `TSchema`（TypeBox），`validateToolArguments()` 在 `agent-loop` 准备阶段校验。
- `Usage` 区分 `input/output/cacheRead/cacheWrite/cacheWrite1h/reasoning`，`cost` 分项计费。
- `DeferredHandle`（`types.ts:410-420`）：`{ provider, modelId, api, id, expiresAt, pollAfterMs, data }`，用于异步长任务（Anthropic/Responses 的 deferred 模式）。

### 2.4 选项与回调

```ts
interface ProviderRequestOptions {
  signal?, telemetryContext?, apiKey?, fetch?, env?, onPayload?, onResponse?,
  headers?: ProviderHeaders, timeoutMs?, maxRetries?, maxRetryDelayMs?
}
interface StreamOptions extends ProviderRequestOptions {
  temperature?, samplingParams?, maxTokens?, transport?, cacheRetention?, sessionId?,
  websocketConnectTimeoutMs?, metadata?
}
interface SimpleStreamOptions extends StreamOptions {
  toolChoice?: "auto"|"none"; reasoning?: ThinkingLevel; deferred?: boolean|{window: "15m"|"1h"|"24h"};
  thinkingBudgets?: ThinkingBudgets;
}
```

`getApiKey` 允许每次 LLM 调用前动态解析短生命周期 token（如 GitHub Copilot 的 OAuth）；`onPayload` 可在发送前替换 payload（用于扩展或网关注入）。

### 2.5 事件流协议（`types.ts:541-563`）

```ts
type AssistantMessageEvent =
  | {type:"start"; partial}
  | {type:"text_start|delta|end"; contentIndex; partial/delta/content}
  | {type:"thinking_start|delta|end"; ...}
  | {type:"toolcall_start|delta|end"; ...}
  | {type:"done"; reason: "stop"|"length"|"toolUse"|"deferred"; message}
  | {type:"error"; reason: "aborted"|"error"; error: AssistantMessage}
```

契约：必先 `start`，`done/error` 终止，`partial` 为 live helper，文本/思考块在 `start` 时为空，仅通过 `delta` 增长，`tool_call` 参数在 `start` 时不完整。

`AssistantMessageEventStream`（`utils/event-stream.ts`）为 `EventStream<AssistantMessageEvent, AssistantMessage>`，`stream()` 返回流，`response.result()` 解析 `message`。

## 3. Provider 与 Api 层

### 3.1 分层

```
providers/<provider>.ts  (e.g. anthropic.ts, openai.ts, google.ts)
    ↓ 创建 Provider 实例，绑定 Model 列表、Auth、Stream 实现
api/<api>.ts             (e.g. anthropic-messages.ts, openai-completions.ts)
    ↓ 实现 ProviderStreams { stream, streamSimple, fetchDeferred?, cancelDeferred? }
    ↓ HTTP(S) / WebSocket 调用 Provider API，产出 AssistantMessageEventStream
```

`providers/all.ts` 导出全量 Provider 列表，`api/lazy.ts` 提供 `lazyApi()` 按需加载（避免打包所有 Api 实现）。

### 3.2 支持的 Provider（`types.ts:35-76` + `providers/` 目录）

`amazon-bedrock`, `ant-ling`, `anthropic`, `google`, `google-vertex`, `openai`, `azure-openai-responses`, `openai-codex`, `radius`, `nvidia`, `deepseek`, `github-copilot`, `xai`, `groq`, `cerebras`, `openrouter`, `vercel-ai-gateway`, `zai`, `mistral`, `minimax`, `moonshotai`, `huggingface`, `fireworks`, `together`, `baseten`, `opencode`, `kimi-coding`, `cloudflare-*`, `qwen-*`, `xiaomi-*` 等 30+。

每个 Provider 目录下有 `<provider>.models.ts`（模型列表）与 `<provider>.ts`（工厂）。

### 3.3 兼容性细节

`OpenAICompletionsCompat`（`types.ts:568-643`）有 20+ 开关，体现了对“OpenAI-compatible 但有差异”的适配深度：

- `supportsStore` / `supportsDeveloperRole` / `supportsReasoningEffort` / `supportsUsageInStreaming` / `supportsFinishReason`
- `maxTokensField` / `requiresToolResultName` / `requiresAssistantAfterToolResult` / `requiresThinkingAsText`
- `thinkingFormat`（6 种：`openai`/`openrouter`/`deepseek`/`together`/`baseten`/`zai`/`qwen`/...）
- `thinkingTokenBudgetField`（`thinking_token_budget` 对 vLLM 等）
- `supportsOpenAIGrammarTools` / `supportsStrictMode` / `cacheControlFormat`
- `sessionAffinityFormat` / `deferredToolsMode="kimi"` / `vllmPriority`

此类细节的系统化，使得 Pi 能在不改上层的情况下接入大量 OpenAI-compatible 网关与自建推理服务。

## 4. 模型发现与目录（`models.ts` / `models-store.ts` / `models.generated.ts`）

- `Models`：模型集合，支持 `models.find(provider, id)` / `models.list()` 等。
- `ModelsStore`：持久化与刷新（`hydrateModelData` / `checkModelData`），数据来源为 `models.generated.ts`（由 `scripts/generate-models.ts` 从各 Provider API 拉取生成，**禁止手改**）。
- `model-catalog`：`ModelCatalog` 为发布用聚合产物（`scripts/generate-model-catalog` / `diff-model-catalog.mjs` / `publish-model-catalog.mjs`）。
- 图片模型：`image-models.generated.ts` / `images.ts` / `providers/images/` 单独管理 `ImagesModel` / `ImagesContext` / `generateImages()`。

`package.json:30-36` 定义 `generate:models` / `hydrate:model-data` / `check:model-data` 等脚本；`AGENTS.md` 要求 `models.generated.ts` 的修改必须通过 `generate-models.ts`。

---

## 5. 鉴权（`auth/` + `oauth.ts` + `env-api-keys.ts`）

- `AuthContext` / `CredentialStore` / `OAuth`：支持 API Key、OAuth Device Code / PKCE、Bun OAuth 等多种流。
- `env-api-keys.ts`：从 `process.env` 解析 `ANTHROPIC_API_KEY` 等约定 key。
- `compat/extension-oauth-types.ts`：扩展可注册的 OAuth 自定义 Provider（`packages/coding-agent` 的 `llama` 扩展即通过此路径注册 Hugging Face Provider）。
- `getApiKey(provider)` 契约允许每次请求前异步刷新短生命周期 token；失败时抛 `authHeader requires a resolved API key`，上层据此提示 `/login <provider>`。

---

## 6. 重试与容错（`utils/retry.ts` / `utils/diagnostics.ts`）

- `retryDelayMs(response.headers, attempt)`：解析 `Retry-After` / `retry-after-ms` 等头部，结合指数退避。
- `isRetryableAssistantError` / `isContextOverflow` / `isRecoverableLength`：供 `agent` / `AgentSession` 判定是否重试或触发 compaction。
- `AssistantMessageDiagnostic`：在 `AssistantMessage.diagnostics` 中保留脱敏后的 Provider/Runtime 诊断，便于排查。

## 7. 与 Agent 的集成契约

| 职责 | 在 `pi-ai` 的位置 | 在 `agent` 的使用 |
|---|---|---|
| 统一消息/工具类型 | `types.ts: Message/Tool/Context` | `agent/types.ts: AgentMessage/AgentTool/AgentContext` |
| 统一模型 | `types.ts: Model<TApi>` | `Agent.state.model: Model<any>` |
| 统一流 | `utils/event-stream.ts` | `agent/stream-fn.ts: StreamFn` |
| 统一鉴权 | `auth/*` + `Models` | `Agent.getApiKey` / `AgentSession.ModelRuntime.getAuth` |
| 错误编码 | `AssistantMessage.stopReason:"error"` | `agent-loop` 检测后 `turn_end` + `agent_end` |

关键原则：`StreamFunction` 永不 throw，失败必须编码进流的 `error` 事件；`convertToLlm`/`transformContext` 不可 throw，必须返回 safe fallback。
