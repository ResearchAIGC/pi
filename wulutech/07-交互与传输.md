> 源码锚点：`packages/tui/src/` / `packages/chord/src/` / `packages/protocol/src/protocol.ts:110` / `packages/client/src/` / `packages/server/src/` / `packages/telemetry/src/` / `packages/session-backends/`

## 1. 为什么要单独成层

编排层（`AgentSession`）已能跑通“输入 → 调模型 → 执行工具 → 落盘”，但还有三类未解：

1. **终端体验**：如何做到输入不粘包、图片与剪贴板跨平台一致、渲染足够快？
2. **应用组合**：`pi` 既是单进程 CLI，又可能被拆成多服务（编辑器插件、远程网关），如何用同一套原语描述？
3. **远程与持久化**：会话如何跨进程存活？远程的字节流如何与本地存储解耦？

分工如下：

- `pi-tui` 回答 1（自研终端界面）。
- `chord` 回答 2（应用组合运行时）。
- `pi-protocol` + `pi-client`/`pi-server` + `session-backends` + `telemetry` 回答 3。

## 2. TUI（`packages/tui` — `pi-tui`）

### 2.1 定位

自研的差分渲染终端界面库。相比 Ink/Blessed，它的特点是组件模型化、布局引擎化、增量渲染。`coding-agent` 的交互模式深度依赖它，但它也可独立使用。

### 2.2 架构

```
TUI（tui.ts）              抽象接口：尺寸、渲染、输入、鼠标、覆盖层
├── TuiMainScreen          主屏：接管标准输出，差分渲染，支持备用屏切换
├── TuiAltScreen           备用屏：全屏覆盖层（如会话选择器）
└── Components             组件：Box、VStack、HStack、Text、ScrollView、Editor 等

Layout（layout.ts）        布局节点树 → 测量 → 排列 → 文本行 → 对比上一帧 → 最小化输出
Input（keys.ts 等）        原始字节 → 切分输入帧 → 按键 → 快捷键 → 动作
Native（terminal-*.ts）    终端能力：颜色探测、图片、剪贴板
```

### 2.3 核心组件与渲染管线

**常用组件**（按使用频率）：

| 组件 | 作用 |
|---|---|
| `VStack` / `HStack` / `Box` | 垂直/水平布局与带边框容器 |
| `Text` / `TruncatedText` | 文本与截断文本 |
| `ScrollView` | 可滚动视口 |
| `SelectList` | 带搜索的选项列表（模型/会话选择） |
| `Input` / `Editor` | 单行/多行输入，`Editor` 支持撤销、kill-ring 等 |
| `Markdown` | 基于 `marked` 的 Markdown 渲染 |
| `Image` | 终端图片（自动选择 Kitty/iTerm2/Sixel 协议） |

**渲染管线**：

```
VStack 树（如 ChatViewport）
  → 测量（考虑可见宽度与 ANSI 转义）
  → 排列（按终端尺寸）
  → 展平为文本行（含光标）
  → 对比上一帧，生成最小重绘序列
  → 写入终端
```

`tui-main-screen.ts` 负责主循环：监听窗口尺寸变化、接管输入、管理覆盖层的层叠。`0.86.0` 起压缩、分支与重试的指示器统一嵌入编辑器边框。

### 2.4 输入与快捷键

- `keys.ts`：定义按键（`id` + 类型 + 修饰键）与解析、匹配函数。
- `keybindings.ts`：定义快捷键到动作的映射。新增快捷键必须加入默认绑定（`DEFAULT_EDITOR_KEYBINDINGS` / `DEFAULT_APP_KEYBINDINGS`），而非硬编码匹配（`AGENTS.md` 约束）。
- `stdin-buffer.ts`：将原始输入字节按“输入帧”聚合，处理粘包与半包。

### 2.5 原生能力

- **剪贴板**：优先用系统原生命令，降级到 OSC 52（`0.86.1` 修复了容器与 WSL 下的回退）。
- **图片**：自动探测终端能力，选择 Kitty、iTerm2 或 Sixel 协议编码（`terminal-image.ts`）。
- **颜色**：探测终端配色（`terminal-colors.ts`）。
- **预编译**：为 macOS、Linux、Windows 分别预编译原生模块（`native/darwin` 等）。

## 3. Chord（`packages/chord` — `chord`）

### 3.1 定位

应用组合运行时（Application Composition Runtime）。它提供四类原语：插件（Facet）、复制状态、可远程调用的服务（RPC）、发布/订阅。Pi 用它组装复杂的多服务应用，但它本身是独立通用库。

### 3.2 四类原语

- **Facet**（`facets/`）：声明式插件。`Facet` 定义 `name`、`services` 与 `load()`，`FacetHost` 是宿主，`FacetLoader` 负责发现与加载。
- **Service**（`services/`）：通过 `defineService()` 定义服务，`RemoteServiceProvider` 发布服务，客户端通过 `createRemoteServiceBinding` 调用。
- **ReplicatedState**（`delta/`）：基于操作日志的可复制状态，支持订阅。`0.86.0` 由原先的 delta tracker 重构为 operation log。
- **Context**（`context/`）：依赖注入容器，贯穿插件与服务。

### 3.3 导出与目录

```ts
// 插件
createFacetHost, createStaticFacetLoader, defineFacet, defineService
// 复制状态
replicatedState
// 远程服务
createRemoteServiceBinding, createRemoteServiceEndpoint, RemoteServiceProvider
// 工具
isJsonValue, JsonValue, JsonRepresentation
```

```
packages/chord/src/
├── api.ts / types.ts / json.ts
├── node.ts / node/          — Node 宿主实现
├── context/                 — 依赖注入
├── delta/                   — 操作日志与复制状态
├── facets/                  — 插件加载与宿主
└── services/                — RPC 协议与编解码
```

## 4. Protocol（`packages/protocol` — `pi-protocol`）

### 4.1 定位

传输中立的 CBOR 协议，用于 `pi-client` 与 `pi-server` 之间的远程会话。只定义帧与信封，不绑定具体传输（可走标准输入输出、Unix Socket、TCP 等）。

### 4.2 版本与握手（`src/protocol.ts:5`）

```ts
export const PROTOCOL_VERSION = 8 as const;
```

客户端首帧必须是 `{ type:"hello", version }`，服务端回应 `{ type:"hello", version:8, serverId }` 或错误。

### 4.3 信封（`src/protocol.ts:28-110`）

```ts
// 目标：服务器或某个会话的某个附件
RpcTarget = ServerTarget { serverId } | SessionTarget { serverId, sessionId, attachmentId }

// 客户端 → 服务端
ClientMessage = ClientHello
              | RequestEnvelope { type:"request", id, target, call: JsonValue }
              | CancelEnvelope  { type:"cancel",  id, target }

// 服务端 → 客户端
ServerMessage = ServerHello | ServerHelloError
              | ResponseEnvelope { type:"response", id, ok, result? }
              | ServiceEventEnvelope { type:"service_update", subscriptionId, update }
              | AttachmentEnvelope   { type:"attachment", attachment }
```

`call` 是任意 JSON 值，使协议可承载任意 Chord 服务的调用；`cancel` 支持取消进行中的请求。

### 4.4 编解码

- `cbor/`：CBOR 编码器/解码器（紧凑二进制，支持 `JsonValue` 全集）。
- `framing.ts`：长度前缀的帧封装，保证流式传输中的消息边界。
- `codec.ts`：`encode(ClientMessage) → Uint8Array` / `decode(bytes) → ServerMessage`。

`0.86.1` 时 `PROTOCOL_VERSION` 未变，无破坏性变更。

## 5. Client / Server

### 5.1 Client（`packages/client` — `pi-client`）

```
client.ts       — PiClient：连接管理、请求与响应的关联
connection.ts   — Connection：帧的收发、重连、心跳
transport.ts    — Transport 抽象（帧字节流）
unix.ts         — Unix Socket 传输
```

传输中立：构造时传入 `Transport`（如 `UnixTransport`），后续所有请求都走该传输。

### 5.2 Server（`packages/server` — `pi-server`，实验性）

```
server.ts            — PiServer：监听、握手、路由
session-router.ts    — SessionRouter：按会话路由到对应附件
listener.ts          — Listener 抽象
transports/unix/     — Unix Socket 监听
```

`SessionRouter` 管理多会话多附件的 `attachmentId`；`AttachmentEnvelope` 带外更新当前选中的会话路径。

## 6. Telemetry（`packages/telemetry` — `pi-telemetry`）

厂商中立的观测契约，定义 Span 与 Event 的强类型 Schema，供 `agent` 与 `ai` 产出一致的可观测数据，再由适配器桥接到具体后端：

```ts
defineTelemetrySchema({ spans: { mySpan: { startAttributes, endAttributes, events } } })
  → TelemetrySchemaDefinition
createTypedSpanStarter(schema, telemetryContext) → TypedSpanStarter<Schema>
InMemoryTelemetryContext / NOOP_TELEMETRY_CONTEXT → 两种实现
```

- `agent` 的循环与 `Harness.Drive` 在每次调模型、执行工具、压缩时产出 Span。
- `ai` 的每个 `api/*.ts` 在 HTTP 调用时产出 Span（含厂商、模型、用量等）。
- 所有 Span 的属性经 `TypeBox` 校验；`testing/` 提供一致性测试套件。

## 7. Session Backends

### 7.1 sqlite-node（`packages/session-backends/sqlite-node`）

Node 原生的 SQLite 后端，实现 `agent` 的 legacy `Storage` 接口，事务保证 `insertEntry + setValue(branchTip)` 的原子性。

### 7.2 JSONL（`packages/agent/src/harness/session/jsonl/`）

文件系统后端：

```
jsonl/
├── codec.ts       — 记录与 JSON 行的编解码
├── io.ts          — 追加写与流式读
├── repo.ts        — 目录级仓库（每会话一个 JSONL 文件）
├── storage.ts     — Storage 实现
├── fork.ts        — 分叉复制逻辑
└── types.ts
```

`StorageBackedSession` 在此之上封装 `MutationLine`（串行化并发写入）与 `IdGenerator`。与 `pi-durable` 的 `MemoryStorage` 区分：前者是现役生产路径，后者是下一代契约的参考实现。

## 8. 协同示例：一次远程调用

```
用户（本地）                PiClient               PiServer               Harness
   │  pi --remote ...          │                       │                       │
   ├── hello(ver=8) ──────────→│── hello(ver=8) ──────→│                       │
   │                           │←─ hello(ver=8, id) ──│                       │
   ├── request(prompt("fix")) ─→│── Lane.prompt() ────→│                       │
   │                           │                       │  Generation → Tools → Response │
   │←─ response ───────────────│←─ service_update ───│←─ HarnessEventBus ────────────│
```

`protocol` 的 CBOR 帧与 `Chord` 的服务绑定共同完成跨进程的服务订阅与调用。
