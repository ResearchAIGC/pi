# 02 — 架构总览：一条请求走完全链路

> 源码锚点：`packages/coding-agent/src/core/agent-session.ts:1175` / `packages/agent/src/agent-loop.ts:156` / `packages/ai/src/types.ts:422` / `packages/durable/src/types.ts:51`

---

## 1. 为什么需要分层

如果只把用户输入发给大模型、把工具结果喂回去，一个 `while (有工具调用)` 循环就够了。长程编码任务会迫使你多回答五个问题：

1. **上下文溢出怎么办**？10 万 token 的对话如何压缩且不丢关键信息？
2. **工具并发与确定性如何兼得**？`read` 三次与 `bash` 两次可以并发跑，但落盘的 `ToolResultMessage` 必须与模型输出的顺序一致，否则重放会乱。
3. **会话如何跨进程存活**？崩溃后能否从最后一条记录恢复？
4. **多模型差异如何收敛**？OpenAI 与 Anthropic 的工具格式、思考块、截断语义都不同。
5. **扩展如何不改内核就介入**？审计、容器化、项目专属命令能否外置？

Pi 用五层回答这些问题，依赖方向严格向下：

```
┌─────────────────────────────────────────────────────────────────┐
│  交互层  pi-tui（差分渲染的终端界面）                               │
│          + chord（插件/状态/RPC 的组合运行时）                     │
│          + protocol（CBOR 帧，传输中立）                          │
│          本地 TUI / --print / --rpc 三种呈现，共用同一 AgentSession│
└────────────────────────┬────────────────────────────────────────┘
                         │  prompt(text) / steer() / followUp()
┌────────────────────────▼────────────────────────────────────────┐
│  编排层  AgentSession + ModelRuntime + SessionManager              │
│          扩展、Skills、压缩、队列、持久化的粘合层                 │
└────────────────────────┬────────────────────────────────────────┘
                         │  Agent.prompt([UserMessage]) / agent-loop
┌────────────────────────▼────────────────────────────────────────┐
│  运行时  Agent（状态与队列）+ agent-loop（双层循环）+ Harness     │
│          Lane/Drive/Storage + pi-durable 新契约                  │
└────────────────────────┬────────────────────────────────────────┘
                         │  streamFn(model, TranscriptContext)
┌────────────────────────▼────────────────────────────────────────┐
│  能力层  pi-ai（Model + TranscriptContext + Message + Tool）      │
│          30+ Provider × 10 Api + 兼容开关 + 事件流               │
└────────────────────────┬────────────────────────────────────────┘
                         │  HTTP(S) / WebSocket
┌────────────────────────▼────────────────────────────────────────┐
│  基础设施  telemetry（观测 Schema）+ session-backends（SQLite/JSONL）│
└─────────────────────────────────────────────────────────────────┘
```

## 2. 一条链路：`prompt("修复 06-TUI 的竞态")`

先用人话概括：用户在终端输入一句话，依次经过“编排层预处理 → 运行时循环 → 能力层调模型 → 持久化落盘 → 交互层渲染”。下图是带代码锚点的完整路径：

```
用户在 TUI 输入 "修复 06-TUI 的竞态" + 回车
  │
  ├─[编排层] AgentSession.prompt()                          // coding-agent
  │   ├─ 1. 斜杠分流：是否命中扩展命令 / Skill / PromptTemplate？
  │   ├─ 2. 输入拦截：扩展的 input 事件可改写或接管输入
  │   ├─ 3. 技能展开：/skill:xxx → <skill> 块 + 相对路径提示
  │   ├─ 4. 若正在流式：按策略决定插入 steering（中途纠偏）或 followUp（收尾追问）
  │   ├─ 5. 鉴权校验：ModelRuntime.getAuth(model) 现场刷新短生命周期 token
  │   └─ 6. before_agent_start：扩展可注入上下文或改写提示词（0.86 起会持久化）
  │        → _runAgentPrompt(messages) → Agent.prompt([UserMessage])
  │
  ├─[运行时] Agent.prompt() → runAgentLoop() → runLoop()   // agent
  │   ├─ a. 准备上下文（提示词、工具、历史消息）
  │   ├─ b. 外层由 followUp 驱动，内层由工具调用与 steering 驱动
  │   │     ├─ turn_start
  │   │     ├─ 若有 steering 消息，先注入到上下文
  │   │     ├─ 调 streamAssistantResponse() 流式获取模型回复
  │   │     ├─ 执行工具批次（含截断检查，并发或串行）
  │   │     ├─ turn_end，检查是否需要提前停止
  │   │     └─ 轮询 steering 队列
  │   └─ c. 无工具调用时检查 followUp 队列，有则继续外层循环
  │
  ├─[能力层] streamAssistantResponse()                       // agent → pi-ai
  │   ├─ 可选：transformContext 剪裁历史
  │   ├─ 必要：convertToLlm 过滤自定义消息 → 纯 Message[]
  │   ├─ 构造 TranscriptContext { messages: [...] }（提示词与工具已在首条 system 消息中）
  │   ├─ 调 streamFn（即 Models.streamSimple 或自定义实现）
  │   │     → providers/<provider>.ts → api/<api>.ts → HTTP(S)
  │   │     → AssistantMessageEventStream（start/text/thinking/toolcall/done/error）
  │   └─ 消费事件流，拼出最终的 AssistantMessage
  │
  ├─[持久化] Agent → AgentSession._handleAgentEvent()        // 内存与文件的双写
  │   ├─ 先通知扩展
  │   ├─ 再通知外部订阅者（TUI）
  │   └─ message_end 时落盘：SessionManager.appendMessage(entry) → Storage.commit
  │        旧路径：JSONL 文件 ~/.pi/agent/sessions/<uuid>.jsonl
  │        新路径：durable Storage.commit([entry/task/input/conversation])
  │
  └─[交互层] TUI 渲染
       ├─ 助手消息增量渲染（text_delta → Markdown）
       ├─ 工具调用的入参与结果（含 diff 着色）
       └─ 队列与压缩等状态条
```

**两个关键约束**：`StreamFn` 永不抛异常，失败必须编码为 `error` 事件与 `stopReason:"error"` 的消息（`packages/agent/src/types.ts:28-32`）；`convertToLlm` 在每次调模型前执行，确保自定义消息永不泄露到模型。

## 3. 五类核心数据结构

### 3.1 统一消息模型（`packages/ai/src/types.ts:422-470`）

这是链路中流转的基本单位：

```ts
type Message = UserMessage | AssistantMessage | ToolResultMessage;
UserMessage       { role:"user", content: (Text|Image)[], timestamp }
AssistantMessage  { role:"assistant", content: (Text|Thinking|ToolCall)[], api, provider, model, usage, stopReason }
ToolResultMessage { role:"toolResult", toolCallId, toolName, content, details: JsonValue, isError }
```

`AgentMessage`（`packages/agent/src/types.ts:326`）在此基础上允许上层通过 TypeScript 的声明合并注入自定义类型（如 `custom`），但 `convertToLlm` 会在发送前过滤掉它们。

### 3.2 TranscriptContext（`0.86` 的变化）

过去用 `Context { systemPrompt, tools, messages }` 三字段分别承载提示词、工具与历史。现在它们被统一收敛到首条 `system` 消息中：

- 首条 `system` 消息的 `content/sections` 是提示词，`toolsAdded/toolsRemoved` 是工具声明。
- `getCurrentSystemPrompt(messages)` 重放所有 `system` 消息即可得到当前提示词。

这样做的好处是：扩展对提示词与工具的修改也能作为一条 `system` 记录持久化，跨重启与分支保留，且能保留提示词缓存的前缀。

### 3.3 AgentState 与 AgentContext

- `AgentState`（`types.ts:334-359`）是可观察的完整状态，包含模型、思考等级、工具、历史、是否流式中等。
- `AgentContext` 是单次运行的快照，仅含 `messages` 与 `tools`。

两者对 `tools`/`messages` 的赋值都会浅拷贝数组，避免外部持有引用被意外修改（`agent.ts:69-88`）。

### 3.4 事件（分两层）

- **Agent 层**（`types.ts:431-446`）：`agent_start/end`、`turn_start/end`、`message_start/update/end`、`tool_execution_start/update/end`。
- **AgentSession 层**（`agent-session.ts:143-186`）：在此基础上追加 `agent_settled`、`queue_update`、`compaction_*`、`auto_retry_*` 等。监听器会按注册顺序被 `await`，并计入运行的结束判定（`agent.ts:544-591`）。

### 3.5 会话图（DAG）

- **旧实现**：`SessionEntry { id: uuidv7, parentId, type: message|custom|compaction|... }` + `branchTip` 地址（`packages/coding-agent/src/core/session-manager.ts:1746`）。
- **新契约**：`EntryRecord { id: number, conversationId, kind, head?, edits? }` + `ConversationRecord { parent?, owner? }` + `TaskRecord` + `Input`（`packages/durable/src/types.ts:51-67`）。`Seq` 是全局提交序号，`head` 标记可见范围的起点。二者的对照见 `03`。

## 4. 并发与容错

### 4.1 工具并发

`ToolExecutionMode` 有 `sequential`（串行）与 `parallel`（并行）两种（`types.ts:41`）。

- 串行：准备、执行、收尾一步接一步。
- 并行：准备阶段仍串行（让 `beforeToolCall` 能按序拦截），执行阶段并发，结束事件按完成顺序发射，但落盘的 `ToolResultMessage` 按模型输出的源码顺序追加，以保证重放确定性（`agent-loop.ts:487-561`）。单个工具可声明 `executionMode:"sequential"` 强制串行（如写文件）。

### 4.2 队列与 Steering

`Agent` 维护两条队列：`steeringQueue`（运行中途纠偏）与 `followUpQueue`（结束后追问），各自有 `all`（一次取空）与 `one-at-a-time`（一次取一条）两种模式。`runLoop` 在每轮结束后先检查前者，外层结束前再检查后者。

### 4.3 重试与压缩

- 可重试错误由 `isRetryableAssistantError` 等判定，失败时指数退避。
- 若模型因长度截断（`stopReason:"length"`），所有工具调用会被视为“参数可能不完整”而直接标记失败，避免执行危险操作（`agent-loop.ts:379-404`）。
- 上下文溢出会触发压缩：`shouldCompact` 判定 → `compact` 生成摘要 → 必要时重跑被中断的轮次。`Harness.Drive` 还额外处理 `retry` 与 `deferred` 等待态。

## 5. 与同类 Agent 的差异

| 维度 | Pi 的做法 | 常见替代 |
|---|---|---|
| 循环模型 | 纯函数循环 + 有状态 Agent + 持久化 Harness 三级分层 | 单体循环 |
| 上下文管理 | 显式可插拔的多级钩子（剪裁、转换、压缩） | 单一截断策略 |
| 扩展 | TypeBox 工具 + 30+ 事件 + 界面覆盖 | 仅 MCP / Function Calling |
| 模型抽象 | 按 Api（协议）组织，自动发现与生成目录 | 手写 Provider 列表 |
| 会话 | 图结构 + 分支 + 追加日志 | 线性历史 |
| 终端界面 | 自研差分渲染 | Ink / Blessed |
| 传输协议 | 自研 CBOR 帧，传输中立 | 仅 HTTP |
