## 2. 核心数据结构

### 2.1 Message 统一模型（`packages/ai/src/types.ts:422-470`）

```ts
type Message = UserMessage | AssistantMessage | ToolResultMessage;

UserMessage       { role:"user", content: TextContent|ImageContent[], timestamp }
AssistantMessage  { role:"assistant", content: (Text|Thinking|ToolCall)[], api, provider, model,
                    usage, stopReason, errorMessage, deferred?, timestamp }
ToolResultMessage { role:"toolResult", toolCallId, toolName, content, details, isError, timestamp }
```

`AgentMessage`（`packages/agent/src/types.ts:326`）在此基础上通过 **declaration merging** 扩展 `CustomAgentMessages`，允许应用注入 `custom` 等自定义消息（`coding-agent` 的 `CustomMessage` 即由此扩展）。

### 2.2 Context / Tool

```ts
Context { systemPrompt?: string; messages: Message[]; tools?: Tool[] }
Tool    { name, description, parameters: TSchema (TypeBox), constrainedSampling? }
```

`AgentTool`（`packages/agent/src/types.ts:387-412`）在 `Tool` 之上增加 `label`、`prepareArguments`、`execute`、`replay`、`executionMode`。

### 2.3 AgentState / AgentContext

`AgentState`（`types.ts:334-359`）是 `Agent` 的可观察状态：`systemPrompt` / `model` / `thinkingLevel` / `tools` / `messages` / `isStreaming` / `pendingToolCalls`。

`AgentContext`（`types.ts:415-422`）是传给 `agent-loop` 的“单次 Run 快照”：`systemPrompt + messages + tools`。

### 2.4 Event 体系

两层事件：

- **Agent 层**（`types.ts:431-446`）：`agent_start/end`, `turn_start/end`, `message_start/update/end`, `tool_execution_start/update/end`。
- **coding-agent 层**（`agent-session.ts:143-186`）：在此基础上增加 `agent_settled`, `queue_update`, `compaction_start/end`, `entry_appended`, `auto_retry_*` 等 15+ 事件。

所有事件都通过 `Agent.subscribe()` / `AgentSession.subscribe()` 订阅，监听器返回的 Promise 会被 **await 且计入 run settlement**（`agent.ts:544-591`）。

### 2.5 Session Entry DAG

`SessionEntry`（`session-manager.ts`）是追加日志的基本单位，`Entry`（`agent/src/harness/session/types.ts`）是持久化的通用表示：`id` + `parentId` + `type`（`message`/`custom`/`compaction`/`branchSummary`/`file`/`modelChange` 等）。`branchTip(name)`（`values.ts`）记录分支当前叶节点，形成 DAG；`Session.search/scanBranch` 支持按 `seq` / `type` / `customType` / `order` 查询。

### 2.6 Harness Lane 与 Operation

`AgentHarness`（`harness/agent-harness.ts:538-612`）管理多个 `Lane`（命名并发域）。每个 `Lane` 内部通过 `LaneState`（`runtime/types.ts`）跟踪：

```
LaneState { tipId, configuration: LaneConfiguration, inbox: LaneQueuedItem[], 
            lastOperationId, operation: { meta: OperationMeta, state: OperationState } }
```

`Operation` 有 `run` / `compaction` / `navigation` 三种 `kind`，`Drive`（`drive/` 目录）是驱动单个 Operation 前进的状态机：`Boundary → Checkpoint → Generation → Tools → Response → Reconcile → …`

## 3. 关键流程

### 3.1 一次 Prompt 的完整路径

```
用户输入 "修复 bug" 
  → AgentSession.prompt()                                    // coding-agent
    → 扩展命令拦截 (/xxx) / Skill 展开 / Prompt Template 展开
    → 输入拦截 (input event) / before_agent_start 钩子
    → Agent.prompt([UserMessage])                             // agent
      → runAgentLoop(prompts, context, config, emit, signal, streamFn) // agent-loop.ts:96
        → convertToLlm(messages) + transformContext            // 可由 Harness/Extension 注入
        → streamFunction(model, llmContext, {apiKey, signal})  // → pi-ai Provider
          → AssistantMessageEventStream (start/text_*/thinking_*/toolcall_*/done/error)
        → 工具执行 (parallel/sequential)                       // beforeToolCall / afterToolCall
        → Turn 结束 → shouldStopAfterTurn / prepareNextTurn / getSteering/FollowUp
        → 循环直到无 tool_calls 且无队列消息
      → Agent.processEvents() 更新 state + 触发订阅者
    → AgentSession._handleAgentEvent() 持久化 + 扩展事件 + 重试/压缩判定
  → TUI 渲染 (assistant-message / tool-execution / diff 等组件)
```

### 3.2 模型调用抽象

```
coding-agent ModelRuntime.getAuth(model) → AuthResult { apiKey, headers, baseUrl, env }
         ↓
agent Loop 创建 llmContext { systemPrompt, messages: convertToLlm(agentMessages), tools }
         ↓
streamFn = Models.streamSimple  (或自定义 StreamFn)
         ↓
ai/providers/<provider>.ts → api/<api>.ts 的 stream/streamSimple
         ↓
HTTP(S) / WebSocket → Provider Streams → AssistantMessageEventStream
         ↓
agent-loop.streamAssistantResponse() 消费 EventStream → AssistantMessage
```

`StreamFn` 契约（`types.ts:28-32`）：**永不抛异常**；失败必须编码为 `AssistantMessageEventStream` 中的 `error` 事件 + `stopReason:"error"` 的 `AssistantMessage`。

### 3.3 会话持久化

```
Agent message_end → AgentSession._handleAgentEvent → SessionManager.appendMessage(entry)
                                              → Storage.commit([insertEntry(entry), setValue(branchTip, id)])
                                                         ↓
                                              JSONL 文件: ~/.pi/agent/sessions/<uuid>.jsonl
                                              或 SQLite: session-backends/sqlite-node
```

`SessionManager` 额外维护 `SessionHeader`（版本、模型、创建时间）、`SessionHeader` 与 `SessionInfoEntry`（`sessionName`）、`ModelChangeEntry` 等元数据；`CompactionEntry` / `BranchSummaryEntry` 也作为 `Entry` 追加，二者通过 `oldLeafId` / `newLeafId` / `commonAncestorId` 记录压缩/分支的语义。

### 3.4 扩展执行

```
pi 启动 → discoverAndLoadExtensions() 扫描 ~/.pi/agent/extensions/*、项目 extensions/
       → loadExtensions(factories) → ExtensionRunner
       → runner.emit("session_start")
       → 每次 Agent turn 前：runner.emitBeforeAgentStart() 可改 systemPrompt
       → 工具调用前后：runner.emitToolCall() / emitToolResult()（可 block / 改写）
       → 消息结束：runner.emitMessageEnd() 可替换 message
       → provider 请求前后：before_provider_request / after_provider_response
```

## 4. 并发与容错

### 4.1 工具并发

`ToolExecutionMode`（`types.ts:41`）有 `sequential` / `parallel`：

- `sequential`：准备→执行→收尾 串行，下一个工具等上一个完全结束。
- `parallel`：所有工具的 `prepare` 串行（以便 `beforeToolCall` 能顺序拦截），`execute` 并发，`tool_execution_end` 按完成顺序发射，但 `ToolResultMessage` 按源码顺序追加，保证 determinism（`agent-loop.ts:487-561`）。

单个工具可覆盖为 `executionMode:"sequential"`（例如写文件工具需要串行化）。

### 4.2 队列与 Steering

`Agent` 维护两个 `PendingMessageQueue`（`agent.ts:125-159`）：`steeringQueue`（中途纠偏）与 `followUpQueue`（收尾后追问），各自有 `QueueMode`（`all` vs `one-at-a-time`）。`runLoop` 在每 `turn_end` 后先排 `getSteeringMessages()`，外层循环结束前再排 `getFollowUpMessages()`。

### 4.3 重试与 Compaction 恢复

- 可重试错误由 `isRetryableAssistantError` / `isRecoverableLength` 判定，指数退避 + `maxRetryDelayMs` 上限。
- `stopReason:"length"` 的消息中所有 tool_calls 被视为可能截断，统一失败（`failToolCallsFromTruncatedMessage`，`agent-loop.ts:379-404`）。
- 上下文溢出触发 `overflow` 压缩：`shouldCompact(tokens, contextWindow, settings)` 判定 → `compact()` 生成 `CompactionEntry`（含 `summary` + `details`）→ `willRetry:true` 时自动重跑被中断的 turn。
- `AgentHarness` 的 `Drive` 额外处理 `retry` / `deferred` 两种等待态（`drive/retry.ts` / `drive/deferred.ts`）。

coding-agent

## 6. 与同类 Agent 的差异

| 维度 | Pi 的选择 | 常见替代 |
|---|---|---|
| 循环模型 | 低层 `agent-loop`（纯函数，事件驱动） + 高层 `Agent`（状态+队列） + 最高层 `AgentHarness`（持久化+Lane）三级分层 | 单体 loop |
| 上下文管理 | 多级：`transformContext` → `convertToLlm` → `prepareNextTurn` → `compaction` 显式可插拔 | 单一截断策略 |
| 扩展 | TypeBox 定义工具 + 30+ 生命周期事件 + UI 覆盖（custom/editor/footer/widget） | 仅 MCP / Function Calling |
| 模型抽象 | `Api` 维度而非 Provider 维度，自动发现 + 生成目录 | 手写 provider 列表 |
| 会话 | DAG + 分支 + JSONL，天然支持 fork / navigate / summary | 线性历史 |
| TUI | 自研差分渲染 + 原生集成（kitty/iTerm2、剪贴板、图片） | 依赖 Ink/Blessed |
| 协议 | 自研 CBOR + framing，传输中立，可走 Unix Socket | 仅 HTTP |
